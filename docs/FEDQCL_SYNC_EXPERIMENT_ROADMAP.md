# Implementation and experiment roadmap for selective synchronization

## Research claim and evidence

Test whether small client statistics can identify full model exchanges that are safe to skip in federated continual learning. A selected client uploads its trained model and receives the server aggregate. A skipped client misses both model transfers. Count any statistics it exchanges. The target is to spend fewer total bytes while preserving final global accuracy and limiting forgetting. The three policies use the client's own history, the federation's previously shared statistics, and current peer statistics. See the [protocol specification](FEDQCL_CLIENT_SYNC_PROTOCOLS.md).

There are two questions to answer. First, at a shared byte budget, do the statistics help select clients whose omission has less impact than established selection methods? Second, at a fixed tolerance for accuracy loss and forgetting, how many bytes can the best policy save relative to full participation? Treat tolerance values as chosen research criteria. For example, consider allowing one percentage point of final accuracy loss and one percentage point of additional average forgetting, with a separate worst-task tolerance. Freeze the criteria before the held-out campaign.

The main hypothesis is that the value of the three signals depends on the regime. Local history should help detect client-specific drift. Server history should help when a difficult or novel stream was already covered by another client. Current peer reports should help when multiple clients change together and represent one another, provided their telemetry cost is justified. These are hypotheses that the experiments can reject.

## Build in four steps

| Step | First implementation | Evidence to proceed |
| --- | --- | --- |
| 1. Instrument the round | Add a direct evaluator for the frozen server model, a message ledger, and a record of which clients were eligible, selected, accepted for aggregation, and sent the aggregate. | Full participation and a seeded random schedule reproduce the expected participation and task timeline. Every model transfer and report is accounted for. |
| 2. Build controllable streams | Generate positive class proportions with a seeded, constrained Dirichlet mode. Produce separate image shards without replacement and retain the requested and realized client similarity matrices. | Each client has all task classes. The sampler actually exposes the intended proportions, and the evaluation inputs are fixed across conditions. |
| 3. Implement the three policies | Give all policies the same bounded statistics and causal observation cutoffs. Add local references, a versioned server reference bank, and a peer representative selector behind one scheduling interface. | The eligibility and communication logs match each protocol for cold starts, gaps, new tasks, stale reports, and rounds with no accepted model. |
| 4. Expand only where supported | Add replay coverage, projected features or updates, and an adaptive budget after simpler signals show incremental predictive value. | New fields improve the ability to predict poor skips on held-out streams at an accounted communication and compute cost. |

At the server round boundary, the proposed interface takes a round context and permitted reports, then returns requested participants, selection reasons, and required report deliveries. The round executor handles local training, accepted uploads, FedAvg, and recipient selection. Keep decision logic independent of training and evaluation. Use independent random generators for partitioning, schedules, and client draws where possible. Capture worker exceptions as structured failures. The existing implementation points are [the server round loop](../system/flcore/servers/serveravg.py), [aggregation and evaluation](../system/flcore/servers/serverbase.py), and [the client training loader](../system/flcore/clients/clientbase.py).

Start with fixed-size current-task class counts and use the same distance across policies, such as total variation on normalized histograms. Add replay counts as a separate ablation. Estimate observed counts from the same bounded sample window for all policies. Class-proportion signals need a training sampler that preserves the intended proportions. Compare against the legacy sampler in a diagnostic. Keep primary runs within the repo's FedQCL client objective and use plain FedAvg plus ordinary experience replay as a separate transfer check.

Keep statistics timing explicit. Method 1 uses local state only before sending a request. Method 2 initially uses the last server record bank received. Test same-round server telemetry separately and evaluate how often it refreshes the bank. Method 3 sees current reports before electing representatives. Report comparisons both with the information each method naturally receives and with server relay and direct peer election fed the same current reports. That comparison isolates who makes the decision and how reports travel from whether current observations improve selection.

The message ledger records round, sender, receiver or recipient count, kind, serialized bytes, model and report versions, and the accounting convention. Include model uploads, aggregate downloads, snapshots, deltas, probes, requests, and any refresh on rejoin. In simulation these are logical bytes under a defined format. Physical network savings need a separate transport measurement. Track client work too because preselection without full local training and withholding an upload after training have different compute costs.

## First result before a full campaign

Use five clients and the existing CIFAR-100 task sequence. Pick checkpoints before and after task boundaries and during stable rounds. At each checkpoint, replay the same round for all ten possible three-client subsets and the full cohort, starting from the same server and client state. Store the validation loss on current and earlier tasks after each candidate aggregation. Use a validation split independent of the final test set. Preserve task memories, model ages, optimizer and replay state. Make the first deterministic reconstruction a prerequisite for interpreting subset effects.

The result yields three diagnostics:

1. **Opportunity:** How much better is the best subset at the same cost than a random subset? A small gap suggests scheduling has little room to improve in that regime.
2. **Predictability:** Do local, server, and peer scores rank subsets by the actual harm? Report rank correlation, loss regret versus the same-budget oracle, and failure rates for old-task or current-task tolerances. For individual trigger scores, also check the ranked fixed-count version so threshold tuning does not dominate this diagnostic.
3. **Interactions:** Can dropping A and B together hurt more than the sum of dropping either alone? Include selected leave-one-out and leave-two-out branches to test this directly. Run some branches forward across a task boundary to see whether one-round validation improvements persist.

Repeat the diagnostic under near-identical clients, strongly separated clients with full class coverage, and shifting similarities. Include a stress case with equal class histograms and deliberately different within-class image distributions. If label counts fail there, test whether projected features or update sketches recover the lost signal. An allocation oracle sees the true stream profiles. An outcome oracle sees counterfactual validation results. Keep both separate from deployable policies.

## Pilot and confirmatory campaign

Start with full participation, random skipping, oldest-first rotation, and the three proposed policies across three stream regimes and three paired seed settings. This is 54 full runs before reuse or follow-up ablations. Treat it as a pilot for debugging, estimating variance, and choosing thresholds and reporting rules. Start at a target of three participants out of five, then sweep two through four for useful methods. A three-of-five policy saves a nominal 40 percent of full model payload when each sync exchanges the same bytes. Report the net savings after all control and refresh traffic.

For confirmation, hold out entire partition seeds and shift schedules and freeze the policies. Choose the number of paired runs using pilot variability and the width of the confidence interval needed to resolve the prespecified tolerance. Give all policies the same round and data schedules. Use two comparisons:

- Fix the selection count per round to isolate the value of selecting different clients. Report telemetry separately and report the resulting difference in total bytes.
- Match total bytes, including telemetry, to test the actual deployment trade-off. Include a rate-matched random schedule that copies the adaptive policy's participant counts per round, using the same gap rules where feasible. This tests the value of client identities separately from when the budget was spent.

Compare with a representative client sampler and a gradient-diversity baseline where feasible. Give each baseline a documented information budget. Charge full gradients if a reproduction actually exchanges them. Declare any use of cached or projected gradients as a variant. [Clustered Sampling](https://proceedings.mlr.press/v139/fraboni21a.html) and [DivFL](https://openreview.net/pdf?id=nwKXyFvaUm) are direct starting points. Compare the decision interface with [Learning to Sync at the Edge](https://arxiv.org/abs/2610.14268), which studies client-side adaptive upload and download decisions. The proposed contribution is a test of redundancy across clients and tasks under a two-way byte budget, including the consequences for replay and forgetting. A novelty claim requires a broader literature review.

Separate the effects of choosing whom to skip, letting updates grow stale, and missing task-boundary replay capture. Run a matched native-rejoin versus paid-refresh comparison and a native versus local replay-capture comparison. Use the same mechanics within each comparison. After a clean five-client result, increase the client count to test when peer telemetry starts to outweigh avoided model exchanges. If the paper makes claims about larger backbones or deployed networks, add an actual larger-model or transport experiment and scope the claims to the observed conditions.

## Results that would support the paper

Use the server's final mean task accuracy and average forgetting as primary outcomes, with worst-task and per-class summaries. Report paired confidence intervals for differences, counting partition and training replicates as the units of replication. Treat round checkpoints as repeated measures within a run. Report results over all prespecified runs with failure codes and show the realized budget. Use a common held-out evaluation set and the known task IDs of the current protocol.

The main figure should show total bytes on the horizontal axis and final server accuracy and forgetting in separate panels. Add a breakdown of upload, download, and statistics bytes, a plot of predicted versus realized subset harm, and a per-task accuracy trajectory. Report the percentage of bytes saved at the chosen tolerance and the improvement over the strongest matched-budget baseline. If the confidence intervals leave room for a practically important loss, report the finding as inconclusive at that tolerance.

A strong result shows a reproducible improvement over matched random, rotation, and representative sampling, explains when telemetry is informative, and survives a controlled shift or a second scale. If it helps only in highly redundant streams, quantify where the advantage begins. If stale reports or peer fan-out erase savings, show where the method should switch to cheaper history or full participation. If the oracle has room to improve but the reports cannot predict it, the next step is to test richer signals rather than spend the campaign tuning the scheduler.
